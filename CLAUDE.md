# Hyper Studio

Hyper Studio, o app web da Hyper Estratégia Digital (agência de estratégia digital: conteúdo, social media, tráfego pago e mais) com Firebase: projeto `hyper-9e023`, Auth, Firestore e Hosting. HTML, CSS e JavaScript puros, sem build. O SDK do Firebase vem do CDN (gstatic).

## Identidade visual: obrigatória

Toda interface deste repositório segue `docs/identidade-visual.md`.
- Use sempre as variáveis CSS do topo de `public/css/style.css` (`--hyper-roxo`, `--cor-primaria`, `--fonte-titulo` etc.). Não escreva cores ou fontes soltas no código.
- Logos e ícones ficam em `public/img/`. Não recrie o logo em SVG ou texto.
- Os originais da marca estão em `docs/marca/` e não são publicados.

## Código

- Estrutura e coleções do Firestore descritas no `README.md`. Uma tela por arquivo em `public/js/views/`.
- Todos os dados ficam no espaço compartilhado `espacos/hyper/<coleção>` e são lidos da memória (`dados` em `db.js`). Não faça consultas com `where`/`orderBy` no Firestore: filtre em memória. `users/{uid}` é só o backup antigo.
- Usuários e permissões: `espacos/hyper/membros/{uid}` com `papel` (`admin`/`basico`/`cliente`), `permissoes` (`conteudo`, `trafego`) e `status` (`pendente`/`ativo`). O Financeiro (valores, contratos, orçamentos, comercial) é só de administrador, também nas regras. `cliente` = pessoa do cliente: usa o portal (`views/portal.js`: Início para aprovar, Calendário, Marca, Resultados, Sugerir post), com `clientes` e, opcionalmente, `marcas` (só essas marcas). Nas regras, `ativo()` é só a equipe; o que o cliente pode fica em `cliente()`/`postDoCliente()`. Use `ehCliente()`/`marcasRestritas()` de `permissoes.js`. Cliente nunca entra nas listas da equipe (responsáveis, menções, resumo diário, agenda). Criativos guardam `marcaId` (o cliente de uma marca só lê os dela). O dono do espaço (conta da Hyper) é sempre admin. Use `pode(area)`, `ehAdmin()` e `tarefaVisivel()` de `permissoes.js` nas telas, e mantenha `firestore.rules` coerente: dados sensíveis (financeiro, contratos, orçamentos, contas de anúncio, manutenções) são protegidos nas regras, não só escondidos na tela.
- Acesso por cliente: `acessoClientes: "alguns"` + `clientes` no membro. Para essas pessoas, `db.js` lê as coleções por cliente (`ouvirColecao`, consultas `where("clienteId", "in", …)` em lotes de 30; `clientes`/`contratos` documento a documento). É a única exceção à regra de não usar `where`, porque as regras exigem a consulta filtrada. Todo documento ligado a cliente precisa ter `clienteId` (use `""` quando não tiver cliente).
- Convites em `convites/{email em minúsculas}`; pedidos em `membros/{uid}.pedido`. A própria pessoa só muda `nome`, `foto` e `pedido` (Minha conta, `views/conta.js`).
- E-mails: `emails.js` + Apps Script (`docs/email/Codigo.gs`). Só administradores enviam (precisam do segredo em `config/email`); sem segredo o script só avisa os administradores. As cores da marca vão escritas em `emails.js` porque e-mail não aceita variáveis de CSS.
- Conexões pessoais (e-mail da agenda, Facebook/Instagram) ficam em Minha conta, não em Ajustes. Tokens (Google, Meta) nunca vão para o banco.
- Excluir sempre por `excluir()` de `db.js`: nas coleções de `COM_LIXEIRA` guarda uma cópia na `lixeira` (30 dias). Para mover dados (não é exclusão de verdade), use `{ lixeira: false }`. O desfazer usa `desfazerExclusao()`.
- Mudanças relevantes em tarefas entram no histórico (`registrarAtividade`); comentários ficam em `tarefas/{id}/atividade`.
- Erros mostrados com `avisar(..., "erro")` e erros não tratados vão para `erros` (Ajustes → Erros recentes).
- Aprovação do cliente: `aprovacoes/{token}` (público por token, expira) e `aprovar.html` + `js/aprovar.js` (sem login). Nunca coloque valores de contrato ou dados internos na fotografia do link.
- Relatórios da Meta: `meta.js` (Graph API pelo navegador, App ID em `config/meta`). Peça cada métrica separada: a Meta aposenta métricas com frequência. Anúncios (Tráfego pago, Beta): `anuncios(idConta, de, ate)` pede `spend`, `reach`, `impressions`, `clicks` e `actions` separados em `act_<id>/insights` (permissão `ads_read`); `numerosAnuncios()` em `views/trafego.js` mostra no cartão do cliente (30 dias) e nos Relatórios. Manutenção atrasada (`manutencoesAtrasadas()`, mais de 7 dias) vira aviso no Hoje de quem é do tráfego.
- Automações (resumo diário, backup) rodam só no Apps Script da conta da Hyper (`docs/email/Codigo.gs`, lendo o Firestore pela API REST como dona do projeto). Backup sempre compacto e sem imagens.
- Valores de contrato (mensalidade, dia de vencimento) ficam em `contratos/{clienteId}`, nunca na ficha do cliente. Use `contrato(clienteId)` de `db.js`.
- Coisas pessoais de cada usuário (Google Agenda conectada) ficam em `espacos/hyper/pessoal/{uid}/...`.
- Datas são texto `AAAA-MM-DD`; use as funções de data de `ui.js`.
- Formulários usam `formulario()` de `ui.js` (campos podem ter `mostrarSe(valores)` e selects podem ter `opcoesDe(valores)`).
- Post = tarefa com `tipo: "Conteúdo"` (`TIPO_CONTEUDO`). Não recrie uma coleção separada de conteúdos. O post tem um status só: a etapa (`statusConteudo`); o `status` de tarefa sai dela (`statusDaEtapa`/`etapaDoStatus` em `constantes.js`).
- Grupos: cliente com marcas é um grupo (guarda-chuva, `marcasDo(id).length > 0`); a identidade de cada negócio (logo, cores, tom de voz…) fica na marca, e a do cliente vale só para os posts institucionais do grupo (sem marca) e completa o que estiver vazio nas marcas. A marca `principal` vem primeiro (`marcasDo`). Para reorganizar use a aba Marca: "Juntar outros clientes como marcas" (`juntarUm`) e "Separar em cliente próprio" (`separarMarca`), em `views/marca.js`.
- Importação: só o briefing da marca, na própria marca (aba Marca → "Importar briefing (JSON)", `views/importarBriefing.js`): o JSON vai para a marca aberta e o `escopo` para o cliente. A outra importação é a do planejamento (Calendário → Planejar → "Importar planejamento (JSON)", `{ posts: [{ data, hora, marca, formato, rede, titulo, pilar, objetivo, roteiro, copy }] }`): os posts do mês entram como rascunho e só gravam em Salvar planejamento; mesma data e título já no planejamento são pulados. Não há outras importações; não recrie importações centrais.
- Marcas: um cliente pode ter várias marcas (`marcas`, com `clienteId`). Post/tarefa guarda `marcaId`. Para o pedido de copy e o PDF use `identidade(clienteId, marcaId)` de `db.js` (marca com o que faltar vindo do cliente). Identidade (logo, Drive, Canva, cores, fontes, sobre a marca, tom de voz, persona, público, palavras, o que evitar, pilares, datas comemorativas, diretrizes) só se edita na aba Marca; não há mais estilo de imagem nem diagramação; as diretrizes (pilares, estrutura, rodapé, hashtags, o que evitar) entram no texto pedido à IA; a aba Marca é dividida em quadros recolhíveis (`quadro()`: Cadastro e contato, Visual, Para a IA, Pilares/datas/diretrizes, com "x de y" preenchidos); cadastro e contato do cliente ficam no quadro Cadastro (`blocoCadastro`); contrato, status e excluir abrem `abrirCliente()` dali. Ficha de grupo: primeiro a tela de escolha da marca (`#/clientes/<id>`), depois a ficha igual à de um cliente comum (`#/clientes/<id>/marca/<marcaId>`, ou `/marca/grupo` para o geral, que tem cadastro, contrato e escopo); a ficha tem só Marca, Campanhas, Escopo e Contas: tráfego (`#/trafego/<cliente>`), resultados da Meta (`#/relatorios/<cliente>`) e financeiro ficam nas telas próprias; use `marcaEscolhida()` de `views/marca.js`. Redes sociais (`CAMPOS_REDES` em `constantes.js`) ficam na aba Contas, da conta aberta; para um post use `redesDe(clienteId, marcaId)` de `views/contas.js`. A ficha do cliente não tem tarefas nem conteúdo: o botão leva para `#/tarefas/<cliente>[/<marca>]`.
- Produzir semana (`producao.js`): os posts da semana do cliente que não são avulsos (`extra` ou `sugeridoPeloCliente`) ficam dentro da tarefa da rotina de produção, como checklist (marcar grava `produzido` no post), e não aparecem soltos no Hoje nem em Tarefas (Tudo/Tarefas); na aba Posts e no calendário aparecem todos. Post criado à mão nasce `extra: true`; os do planejamento, não. Use `dentroDaProducao()`/`postsDaProducao()`. Vídeo (`FORMATO_VIDEO`): o roteiro dos vídeos da semana S entra no Produzir semana de S-7 (`roteirosDaProducao()`, campo `roteiroPronto`). O card avisa posts perto da data (`postsAtrasando()`) e tem Mandar para aprovação (link da semana: `gerarLinkAprovacao(cliente, semana, undefined, { lista, rotulo })`), Copiar legendas e Copiar para outra semana.
- Menus configuráveis (Ajustes → Menus e listas, `config/listas`): `TIPOS_TAREFA`, `FORMATOS`, `REDES` e `ANTECEDENCIA` (dias de produção antes da publicação, por formato) são trocados no lugar por `aplicarListas()` a cada render; Conteúdo e Reunião são fixos (`TIPOS_FIXOS`). Nos selects use `comAtual(lista, valorAtual)` para não perder um valor que saiu da lista. Prazo do post: `prazoDoPost(data, formato, hoje)`. Padrão dos formatos: Estático, Carrossel, Vídeo, Story, Anúncio, Artigo, E-mail marketing, WhatsApp, Blog, Outro; os antigos são convertidos por `migrarFormatos()` (`FORMATO_ANTIGO`).
- Pilares de conteúdo: campo `pilares` da identidade (um por linha, `pilaresDe()` em `ia.js`); o post guarda `pilar`; o calendário com um cliente filtrado mostra os pilares do mês.
- Post em "Em aprovação" guarda `aprovacaoDesde`; o Apps Script (`lembrarAprovacoes`, junto do resumo diário) manda lembrete ao usuário cliente depois de 2 dias (`lembreteAprovacaoEm`). No portal as etapas usam `rotuloEtapaCliente()`.
- Tipos de tarefa: os de `TIPOS_TAREFA` ("Reunião" vira compromisso; "Outro" é o último). Tipos antigos são convertidos por `migrarTipos()`; listas salvas antigas, por `atualizarListas()` (`config/listas.versao`).
- Tarefas concluídas há mais de 90 dias vão para `tarefasArquivo` (`arquivarAntigas()`, só admin). Telas que olham meses antigos usam `todasTarefas()` e `garantirArquivo(data)`/`carregarArquivo()`.
- Ações que apagam ou concluem oferecem desfazer: `avisar(msg, "ok", { desfazer })`.
- Planejamento é um modo do Calendário (`#/calendario/<cliente>/<mês>/planejar`). As rotas `#/planejamento`, `#/criar` e `#/studio` só redirecionam.
- Rotina de cobrança cria a receita `mens-<cliente>-<mês>` (`garantirMensalidade`) e concluir a tarefa marca como paga (`quitarCobranca`).
- Arquivos da marca (logos, fontes, referências) ficam na pasta do Drive do cliente (`linkDrive`). Criativos dos posts ficam em base64 em `clientes/{id}/artes` (`arquivos.js`), não no Firebase Storage (plano Spark). O post guarda os ids (`artes: [ids]` + `qtdArtes`): leia só esses (`listarArtesTarefa`, `artePrincipal(posts)` para PDF e link), nunca a subcoleção inteira; `indexarArtes()` (admin ao entrar) grava os ids nos posts antigos. No portal, post publicado sem imagem mostra o aviso com o link da rede.
- Rotinas (`recorrencias`) têm `modelo`: `livre`, `producao` (semana seguinte), `planejamento` (mês seguinte) ou `cobranca` (vencimento do cliente). A lógica fica em `recorrencias.js`.
- Compromissos (`compromissos`, `agenda.js`, `compromissos.js`) são a única coisa que vai para a Google Agenda. Quem cria os eventos é o Apps Script da Hyper (`sincronizarAgenda` em `docs/email/Codigo.gs`, a cada 5 min ou quando o app pede `agenda-agora`): agenda "Hyper · Compromissos" da conta da Hyper, com convite para `emailAgenda || email` de cada participante. Usa o serviço avançado Calendar do Apps Script e atualiza o MESMO evento (`Events.patch` com `sendUpdates: "all"`), para todos receberem a mudança. O app pede a sincronização sozinho ao salvar/excluir (`sincronizar()` em `agenda.js`). O app não chama a API do Google Calendar. Posts nunca vão para a agenda.
- Cor principal do cliente = `paleta[0]` (também gravada em `cor`); use `corCliente()` de `views/componentes.js`. Campos de cor usam `campoCor()` de `ui.js` (sempre mostram a cor, não só o código).
- Tarefas têm `responsavel` (equipe = membros do espaço + pessoas sem conta em `config/equipe`). Tarefa do tipo "Reunião" vira compromisso.
- Exportação para o cliente é só PDF. Arte final é feita no Canva, fora do app, e anexada ao post como criativo final.
- IA só para criar copy e texto (`ia.js`): o app não chama nenhuma IA e não gera imagem (Criar arte, Studio, OpenAI, Creators e os botões de "sugerir melhoria" saíram; não os traga de volta sem pedido). O botão "✨ Criar copy" (post e Sugerir do portal) e "✨ Criar texto" (tarefa que não é post, campo `texto`) montam o pedido em camadas (`montarPedido(tipo, ctx)`, tipo por `tipoDoPedido(post)`: copy, roteiro, carrossel, stories, videoGravado, anuncio, artigo, email, whatsapp ou texto: papel → manual da Hyper (`manualAtual()`, `config/manual`, padrão em `manual.js`) → marca (`identidade`, sem o visual; diretrizes com `[Formato]` só nesse formato, `diretrizesPara`) → exemplos (`exemplosDaMarca`: os marcados com `exemplo`, senão os aprovados) → campanha (`campanhaId`) → o conteúdo (datas de `datas.js`: feriados, comerciais e as da marca, objetivo do funil `OBJETIVOS`, transcrição do vídeo gravado, posts da semana) → regras do formato/rede → marcadores de resposta → checklist curto). A pessoa cola na IA dela (`levarParaIA`, Claude ou ChatGPT) e cola a resposta de volta (`lerResposta` + `camposDaResposta`: [LEGENDA] → copy; roteiro/lâminas/sequência/texto da arte → `textoArte`). A janela é `abrirAssistenteIA()` (`views/assistenteIA.js`). Também `completudeMarca` (medidor) e `ajustesPedidos` (o ajuste vira regra sempre, só num formato ou só na campanha). Mude os pedidos só em `ia.js`.
- Campanhas (`campanhas`, `views/campanhas.js`, aba Campanhas da ficha): agrupam posts e tarefas (`campanhaId`); só a equipe vê. Escopo do cliente (`clientes.escopo`, aba Escopo, `views/escopo.js`): serviço, frequência, quantidade e quem faz; grava também `servicos` (o que a Hyper faz), que Rotinas e Tráfego usam; `postsPorSemana()` alimenta o aviso do Produzir semana.
- Datas (`datas.js`): feriados nacionais (calendário de todos), datas comerciais, campanhas do mês e as datas comemorativas de cada marca (campo `datas` da identidade, editado na aba Marca: `{ quando: "MM-DD" | "MM" | "AAAA-MM-DD", nome }`). Use `datasEntre(inicio, fim, { clienteId, marcaId })` no calendário, no planejamento e no pedido de copy.
- Link de aprovação: posts ainda em "ideia" vão como tema (`tema: true`); tema aprovado vai para "Em produção".
- Faxina automática (`limparAntigos`, admin ao entrar): lixeira e erros com mais de 30 dias e links de aprovação vencidos há mais de 7 dias (com as imagens); e, uma vez por dia, os criativos (imagens) dos posts publicados há mais de 7 dias (`limparCriativosPublicados()` em `arquivos.js`, `DIAS_CRIATIVOS`): o texto do post fica (vai para `tarefasArquivo` depois de 90 dias). Ajustes: cada quadro recolhe (`recolhivel()`), backup por último. Migrações em `migracoes.js` só normalizam (tipos, formatos, etapa e listas); não crie migrações de uma vez só sem tirá-las depois.
- Nunca coloque chaves no código: o repositório é público.

## Próximos passos

- `docs/proximos-passos.md` é o registro interno do que ficou para depois (fila curta, ideias que saíram e podem voltar, sugestões e pendências de configuração). Quando o usuário pedir "o próximo passo", leia esse arquivo e recomende um passo com o porquê. Ao terminar algo, mova para "Feito"; ao surgir ideia nova, anote. Sem dados de clientes (o repositório é público).

## Publicação

- Um push no `main` roda os testes e publica o Hosting pelo GitHub Actions (`.github/workflows/deploy.yml`, secret `FIREBASE_SERVICE_ACCOUNT`). Pull requests rodam só os testes.
- Testes: `testes/regras.test.mjs` (regras no emulador) e `testes/telas.spec.mjs` (Playwright com o Firebase em memória de `testes/mocks`). Ao mudar `firestore.rules` ou uma tela, atualize os testes. Os dados de teste são fictícios: nunca coloque dados de clientes no repositório.
- O deploy publica também as regras do Firestore (passo que pode falhar sem derrubar o site, se a conta de serviço não tiver o papel de administrador de regras). Quando `firestore.rules` mudar, confira no Actions se o passo "Publicar regras" passou; se não, avise o usuário para colar as regras no console.
- Evite consultas que exijam índice composto, ou avise o usuário para criar o índice.
